# 提案與報價

## 檔案位置與命名

所有提案相關檔案放在 `03-proposal/`：

```
03-proposal/
├── proposal-v1.md         # 提案書
├── proposal-v2.md         # 提案書修訂版
├── quotation-v1.xlsx      # 報價單
├── quotation-v2.xlsx      # 報價單修訂版
└── contract/              # 正式合約
    └── contract-signed.pdf
```

版本管理用 `-v1`、`-v2`，永遠不要覆蓋舊版本。

## 提案書標準結構

```markdown
# [專案名稱] 提案書

> 版本：v1
> 日期：YYYY-MM-DD
> 提案方：Solululab

## 專案背景

（客戶的問題與需求，用客戶能理解的語言描述）

## 解決方案

（我們打算怎麼做，技術方案的高層概述）

## 工作範圍

### 包含項目
1. [具體功能/工作項目]
2. ...

### 不包含項目
1. [明確排除的項目]
2. ...

## 時程規劃

| 階段 | 內容 | 預計工時 | 時間 |
|------|------|----------|------|
| 需求確認 | | | |
| 設計與規格 | | | |
| 開發 | | | |
| 測試 | | | |
| 上線與交付 | | | |

## 報價

（引用報價單，或直接列出總價與付款方式）
```

## 報價估算指引

估算工時時注意：

1. **拆解到可估算的粒度**：每個工作項目不超過 40 小時（5 個工作天）
2. **加上 buffer**：
   - 需求明確的項目：加 20% buffer
   - 需求模糊的項目：加 30-50% buffer
   - 全新技術/未做過的東西：加 50% buffer
3. **不要漏掉**的隱藏成本：
   - 環境建置與部署設定
   - 客戶溝通與會議時間
   - 測試與修 bug
   - 文件撰寫
   - 上線後的問題處理

## 報價修改流程

當客戶要求調整報價時：

1. 新建版本檔案（`-v2`、`-v3`）
2. 在新版本開頭註明與上一版的差異
3. 如果是因為範圍調整，同步更新提案書的「工作範圍」
4. 保留所有歷史版本，不刪除

## 合約簽署後

1. 正式合約放入 `contract/`
2. 在 README.md 更新「合約簽署」里程碑的實際日期
3. 提醒：從此刻起，任何範圍變更都必須記錄在 `05-execution/change-log.md`
