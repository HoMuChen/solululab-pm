# 規格與設計

## 檔案位置

所有規格文件放在 `04-spec/`：

```
04-spec/
├── spec.md              # 功能規格書
├── architecture.md      # 系統架構
└── timeline.md          # 執行時程與里程碑
```

## 功能規格書（spec.md）

### 撰寫原則

- 具體到可以直接開發，避免「彈性處理」、「視情況而定」這類模糊描述
- 每個功能都要定義清楚：輸入是什麼、處理邏輯是什麼、輸出是什麼
- 例外情況和邊界條件要列出來
- 與 `02-requirements/requirement-doc.md` 的需求項目要能對應

### 標準格式

```markdown
# [專案名稱] 功能規格書

> 版本：v1
> 最後更新：YYYY-MM-DD
> 狀態：撰寫中 / 內部審閱 / 客戶確認中 / 已確認

## 系統總覽

（一段話描述整個系統做什麼）

## 功能規格

### F-001：[功能名稱]

**對應需求**：requirement-doc.md #1

**描述**：（這個功能做什麼）

**使用者流程**：
1. 使用者做 A
2. 系統回應 B
3. ...

**輸入**：
- 欄位名 / 型別 / 必填與否 / 驗證規則

**處理邏輯**：
- 步驟 1
- 步驟 2

**輸出**：
- 成功時：...
- 失敗時：...

**例外處理**：
- 情境 A → 處理方式
- 情境 B → 處理方式

### F-002：[功能名稱]
- ...
```

## 系統架構（architecture.md）

### 應包含

- 技術棧選擇與理由
- 系統架構圖（可用文字描述或 Mermaid）
- 主要元件與職責
- 資料流
- 第三方服務整合
- 部署架構
- 安全性考量

## 執行時程（timeline.md）

### 標準格式

```markdown
# [專案名稱] 執行時程

> 最後更新：YYYY-MM-DD

## 里程碑

| # | 里程碑 | 預計日期 | 交付物 | 狀態 |
|---|--------|----------|--------|------|
| M1 | 環境建置 | YYYY-MM-DD | 開發/測試環境就緒 | |
| M2 | 核心功能 | YYYY-MM-DD | F-001, F-002 完成 | |
| M3 | 完整功能 | YYYY-MM-DD | 所有功能完成 | |
| M4 | 測試完成 | YYYY-MM-DD | 測試報告 | |
| M5 | 上線 | YYYY-MM-DD | 正式環境部署完成 | |

## 詳細排程

### 第 1-2 週：環境建置
- [ ] 任務 1
- [ ] 任務 2

### 第 3-4 週：核心功能開發
- [ ] F-001：[功能名]
- [ ] F-002：[功能名]

（依此類推）
```

### 排程注意事項

- 每個里程碑之間預留 buffer（至少 10-20%）
- 不要把每天都排滿，保留處理突發狀況的空間
- 標注關鍵依賴：哪些任務必須等客戶確認才能開始
- 如果有第三方依賴（API、服務、硬體），標注風險

## 規格確認流程

1. 內部撰寫完成後，先自行審閱
2. 與客戶進行規格審閱會議
3. 客戶確認後，在文件中標記「已確認」及日期
4. 確認後才進入執行階段
5. 後續任何變更都必須走變更流程（見 pm-execution skill）
