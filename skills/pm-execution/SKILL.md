# 執行期追蹤

## 檔案位置

```
05-execution/
├── change-log.md        # 變更紀錄（最重要的文件）
├── issues.md            # 問題追蹤
└── deliverables/        # 交付物
```

## 變更紀錄（change-log.md）

這是執行期間**最重要的文件**，保護雙方權益。任何偏離原始規格的變更，不管多小，都必須記錄。

### 每筆變更的格式

```markdown
## CR-001：YYYY-MM-DD — [變更標題]

- **變更內容**：（具體描述變更了什麼）
- **提出者**：（客戶 / 我方 / 雙方討論）
- **原因**：（為什麼需要這個變更）
- **影響範圍**：
  - 時程影響：（延後 X 天 / 無影響）
  - 成本影響：（追加 X 元 / 無影響）
  - 其他功能影響：（列出受影響的功能）
- **是否需追加報價**：是 / 否
- **客戶確認狀態**：✅ 已確認（YYYY-MM-DD）/ ⬜ 待確認
- **對應規格**：spec.md F-XXX

---
```

### 觸發記錄的情境

以下情境**一定要寫 change-log**：
- 客戶說「可以順便加一個...」
- 客戶說「這邊改一下應該很快吧」
- 開發過程發現原始規格有遺漏
- 技術原因導致需要調整實作方式
- 第三方 API/服務異動影響原始設計

### 應對話術建議

當客戶提出變更時，建議的回應模式：
1. 先回應「好的，我記錄下來」（不要當場說行或不行）
2. 評估影響範圍
3. 正式回覆：影響評估 + 是否需要追加報價
4. 取得客戶書面確認後才執行

## 問題追蹤（issues.md）

### 格式

```markdown
# 問題追蹤

## 進行中

### ISS-001：[問題標題]（YYYY-MM-DD）
- **描述**：
- **嚴重程度**：高 / 中 / 低
- **影響**：
- **目前狀態**：調查中 / 等待客戶回覆 / 修復中
- **負責人**：

## 已解決

### ISS-001：[問題標題]（YYYY-MM-DD → YYYY-MM-DD）
- **解決方式**：
```

## 交付物管理（deliverables/）

- 每次交付的檔案放在 `deliverables/` 下
- 如果有多次交付，可用子資料夾：`deliverables/m1-環境建置/`、`deliverables/m2-核心功能/`
- 交付時更新 README.md 的里程碑狀態

## 每週例行

提醒使用者每週至少做一次：
1. 更新 README.md 的「最近活動」和專案狀態
2. 檢查 `issues.md` 有沒有待處理的問題
3. 確認 `change-log.md` 是否有漏記的變更
