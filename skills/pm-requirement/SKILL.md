# 需求整理與問題追蹤

## 需求文件（requirement-doc.md）

位置：`02-requirements/requirement-doc.md`

### 撰寫原則

- 用自己的語言重新描述需求，不是直接複製客戶的話
- 明確區分「客戶確認的需求」和「我方建議的功能」
- 每項需求標注來源（哪次會議、哪份文件）
- 需求確認後標記日期

### 標準格式

```markdown
# [專案名] 需求文件

> 最後更新：YYYY-MM-DD
> 狀態：草稿 / 客戶審閱中 / 已確認

## 專案目標

（用 2-3 句話描述這個專案要解決什麼問題）

## 功能需求

### 1. [功能名稱]
- **描述**：
- **來源**：（哪次會議/哪份文件提到的）
- **優先級**：必要 / 重要 / nice-to-have
- **狀態**：⬜ 待確認 / ✅ 客戶已確認（YYYY-MM-DD）

### 2. [功能名稱]
- ...

## 非功能需求

（效能、安全性、可用性、相容性等）

## 限制條件

（預算、時程、技術限制、第三方依賴等）

## 排除項目

（明確列出不在此專案範圍內的東西）
```

## 問題追蹤（questions.md）

位置：`02-requirements/questions.md`

### 狀態標記

- ⬜ 待確認
- ✅ 已確認（附日期）
- 🔄 已變更（附日期與原因）

### 新增問題的格式

```markdown
- ⬜ [具體問題描述] — 來源：[哪次會議/討論] — 預計在 [日期/場合] 確認
```

### 更新問題的格式

```markdown
- ✅ [問題描述] — 已確認（YYYY-MM-DD）：[確認的結論]
- 🔄 [問題描述] — 已變更（YYYY-MM-DD）：[原本是...，改為...]
```

## 客戶原始資料（client-inputs/）

位置：`02-requirements/client-inputs/`

### 管理原則

- 客戶提供的原始檔案一律放在此資料夾，**不修改原檔**
- 檔案命名加上日期前綴：`YYYY-MM-DD_原始檔名`
- 如果客戶提供的是口頭說明，整理成 `.md` 檔也放在這裡，標題標明「客戶口述」

## 工作流程

1. 收到客戶資料 → 原檔放 `client-inputs/`
2. 閱讀理解後 → 整理到 `requirement-doc.md`
3. 有不確定的地方 → 新增到 `questions.md`
4. 每次會議後 → 更新以上三者的狀態
5. 需求全部確認後 → 在 requirement-doc.md 標記「已確認」及日期，準備進入提案階段
